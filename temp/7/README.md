# Baste & Tanja — wedding invitation

A mobile-first invitation site. Static files only: open `index.html` in a browser,
or drop the whole folder on Netlify, Vercel, GitHub Pages, or any web host.
No build step, no framework, no server.

```
index.html
assets/css/styles.css
assets/js/main.js
assets/fonts/          Fraunces + Karla (self-hosted, SIL OFL)
assets/img/            placeholder photographs — replace these
tools/                 script that generated the placeholders
```

---

## Design direction

The invitation is built out of Filipino wedding materials rather than generic
stationery: a **narra-wood tabletop**, **piña-cloth paper**, a **capiz-shell**
glow behind the envelope, **pine-green wax**, and **brass** hairlines. The
sampaguita sprig laid across the envelope is the one decorative motif and it is
used once. Display type is **Fraunces**; body and interface type is **Karla**.

The signature moment is the envelope itself — it is the whole hero, and the
choreography exists only there. Everything below it stays quiet.

## Editing the content

Almost everything is plain text in `index.html`. The few values that live in
code are at the top of `assets/js/main.js`:

```js
var CEREMONY      = new Date('2026-12-19T15:00:00+08:00');  // countdown target
var RSVP_ENDPOINT = '';                                     // where replies go
```

**Colours** are CSS custom properties at the top of `assets/css/styles.css`
(`--narra`, `--pina`, `--capiz`, `--ink`, `--wax`, `--brass`). The dress-code
swatches are set inline in the HTML so they can be changed independently.

**Maps** — each venue's `.map` element carries a `data-src`. Swap in the embed
URL for your venue and update the matching *Open in Google Maps* link.

## Collecting replies

`RSVP_ENDPOINT` is empty out of the box: the form validates, confirms, and logs
the reply to the browser console so you can test the flow end to end. Guests'
replies are **not** stored until you point it somewhere.

Set it to any URL that accepts a `POST` with a JSON body — Formspree, Getform,
Basin, a Google Apps Script web app, or your own handler:

```js
var RSVP_ENDPOINT = 'https://formspree.io/f/YOUR_ID';
```

The payload is:

```json
{ "name": "", "attending": "yes|no", "guests": "", "companion": "",
  "diet": "", "message": "", "sentAt": "ISO-8601" }
```

If the request fails, the guest is told plainly and the form stays filled in so
they can retry.

## Replacing the photographs

The images in `assets/img/` are abstract placeholders, generated by
`tools/make_placeholders.py`. Drop real photographs in using the same filenames,
dimensions and aspect ratios and nothing else needs to change:

| file | used for | ratio |
|---|---|---|
| `photo-01` | lead photograph under the invitation | 3:4 portrait |
| `photo-02` | gallery, large portrait | 4:5 |
| `photo-03`, `photo-05` | gallery, the pair | 4:5 |
| `photo-04`, `photo-08` | gallery, wide | 3:2 |
| `photo-06`, `photo-07` | overlapping printed pair | 4:3 / 4:5 |

Each photograph needs two files — `name.webp` at full size and `name-640.webp`
at 640px wide — because the `srcset` serves the small one to phones. Keep the
`width` and `height` attributes accurate so nothing shifts while loading.

Also update each `alt` description; they are written for screen readers and for
guests on connections where images never arrive.

## How the mobile requirements were met

**Opening** — the scene is `100svh` so the address bar can't clip it, and page
scroll is held until the seal is tapped, so nobody scrolls past the envelope
without knowing what it is. The envelope is `min(90vw, 520px)`; the wax seal's
touch target is at least 44×44px even where the wax reads smaller. The card
rises 36% of its height and stops, so the important line is on screen and the
page falls straight into normal scrolling — the scroll unlocks about 250ms
after the tap, not when the animation ends.

**Touch** — every interaction is a tap or a vertical swipe. Hover exists only
as a desktop garnish and never hides anything. The seal compresses, buttons
depress and photos scale on `:active`, so feedback lands within a frame.

**Navigation** — a floating monogram button opens a bottom sheet with large
targets; it closes on selection, on tapping outside, and on Escape, and it
tucks itself away while someone is filling in the RSVP so it can never sit on
top of a field.

**Scrolling** — never hijacked. No snapping, no section locking, no horizontal
scrolling anywhere. Reveals are `IntersectionObserver` plus `opacity` and
`transform` only.

**Performance** — no WebGL, no blur filters, no fixed backgrounds, no
libraries. Total first load is roughly 130KB including fonts; the gallery is
lazy-loaded and the map iframes are not fetched at all until *Explore map* is
tapped, which also stops the map from swallowing a scroll.

**RSVP** — single column, 16px inputs so iOS Safari does not zoom, generous
padding, visible labels, autofill, errors beside the field they belong to.
Declining hides guest count, companion and dietary fields; accepting reveals
them and the hidden fields leave the tab order entirely.

**Accessibility** — semantic controls throughout, visible focus rings, skip
link, focus trapped and restored in the sheet and viewer, labelled sections.
Under `prefers-reduced-motion: reduce` the envelope choreography becomes a
plain reveal and the scroll animations are switched off.

**Resilience** — with JavaScript disabled the full invitation is still readable;
if the script fails to load, the page unlocks itself rather than trapping
anyone on the opening scene.

## Verified at

320×568 · 360×800 · 375×667 · 390×844 · 393×852 · 412×915 · 430×932 ·
768×1024 · 1366×768 · 1440×900, in portrait and landscape.

Every viewport was checked for horizontal overflow, clipped text, touch targets
under 44px, and console errors. There is zero horizontal scrolling at any width.
The interaction suite covers the envelope, the sheet, the lightbox including
swipe, the map gating, and the full RSVP flow, plus the reduced-motion and
no-JavaScript paths.
